# Tamyr · сценарий демо — 5 минут

**Подготовка (до выхода):** `cp .env.example .env` (вписать ключ), `docker compose up --build` уже запущен, http://localhost:8000 открыт, в `.env` рабочий ключ,
вкладка браузера во весь экран, отметки аналитика сброшены. Запасной вариант: `python run.py && uvicorn api.main:app`.

## 0:00–0:40 · Проблема и ответ

> «Банку известен 81 клиент — нижний уровень, “курьеры”. Реальная сеть — 2 248 узлов. Аналитик тратит часы на один узел.
> Tamyr — по-казахски «корень» — за 20 секунд отвечает на вопрос: **кого смотреть первым и почему**».

Показать: шапку (2 248 узлов, 81 seed, 365,9 млн ₸), общий вид сети — цвет = роль, размер = приоритет, рамка = seed.

## 0:40–1:40 · Узел №1: сборщик второго уровня `…115284`

Клик по первому месту топ-листа.

- Роль **coordinator, сборщик 2-го уровня**: платят 7 узлов-хабов, деньги 11 seed сходятся сюда.
- «Окрестность» → **схема потока**: слева плательщики (почти все — координаторы), справа — куда уходит.
- «2 шага» → **цепочка денег**: два уровня вверх — видно, как 45 плательщиков второго уровня собираются через 8 хабов.
- **Из чего сложился приоритет**: столбики роли, денег, охвата seed, центральности.
- **Устойчивость роли 100%** — роль не меняется при любых порогах ±20%.

> «Это не курьер — это точка, куда стекаются деньги от других сборщиков. Именно такие узлы нужно проверять первыми».

## 1:40–2:30 · Узел №2: деньги «из ниоткуда» `…331309`

Поиск `331309`.

- Отдал **23 млн ₸** 99 получателям при видимом входе 985 тыс ₸ → предупреждение «есть источники вне выборки».
- Вкладка **«Пробелы»**: узел в первой тройке списка «что запросить дальше» — нужны его входящие из-за пределов выборки.
- Устойчивость роли 75%, альтернатива — distributor: **инструмент честно показывает, где вывод пограничный**.

> «Мы не только ранжируем — мы говорим, каких данных не хватает и какой запрос сделать следующим».

## 2:30–3:10 · Лаборатория порогов — главный момент

- «Лаборатория порогов» → двигаем «Консолидатор: мин. плательщиков» с 5 до 3.
- Граф перекрашивается мгновенно, изменившиеся узлы — с янтарной обводкой; справа: было → стало, кто сменил роль.
- «Сбросить» → 0 расхождений: лаборатория вызывает ту же функцию правил, что и пайплайн.

> «Каждая роль — правило с порогом. Вы можете сами проверить, от чего зависит вывод. Это объяснимость, которую можно потрогать».

(Если остаётся время: «Потоки» — санкей по коленам и ролям; «Июль по дням» — проигрыватель переводов.)

## 3:10–3:50 · AI-ассистент (только по данным графа)

Вкладка «Ассистент», по очереди:
1. «Кто собирает деньги с seed 100000000343175100, 100000004269433100, 100000008418835100?» → находит `…115284`,
   внизу видна цепочка вызванных инструментов.
2. «Что будет с сетью, если заблокировать топ-10?» → эти 10 узлов держат 16% оборота; без них 12% клиентов перестают быть достижимы от seed.

> «LLM не классифицирует — только вызывает наши функции графа и пересказывает результат со ссылками на gid».

## 3:50–4:30 · От гипотезы к действию

В карточке `…115284`: **«на проверке»** + комментарий → в топ-листе появляется отметка.
Кнопка **Досье** → инфографика: движение денег (7 координаторов → клиент → 2 получателя), контрагенты, календарь,
сальдо, признаки, рекомендуемые запросы. «Печать / PDF» — готовый документ для запроса в правоохранительные органы.

## 4:30–5:00 · Почему этому можно доверять

- Каждая роль — формальное правило с порогом (README, `config.yaml`); evidence у всех 2 248 узлов.
- **Устойчивость ролей** к порогам ±20% — средняя 97%; лаборатория порогов показывает это вживую.
- **Заложенная схема**: встроили в реальный граф группу с известными ролями — распознана на 100% в 10 прогонах,
  на случайном шуме ложных хабов 0 (`docs/validation.md`), 8 автотестов.
- Учтены все ограничения данных: обрыв 4-го колена (444 узла → boundary, а не ложный terminal), неполный вход у seed.

## Вопросы жюри — заготовки

| Вопрос | Ответ |
|---|---|
| «Почему у gid X такая роль?» | Открыть карточку: evidence + правило из README + устойчивость. Роли проверяются по порядку, первая выполненная — назначается. |
| «Почему порог 5, а не 4?» | Порог выбран по распределению (99-й перцентиль in_deg = 6). Открыть лабораторию, поставить 4 и показать, сколько узлов меняют роль. Порог меняется в `config.yaml` без правки кода. |
| «Как с 444 узлами 4-го колена?» | Отдельная роль boundary: их исходящие не выгружались; при строгом словаре — `use_boundary_role: false`. |
| «Как проверяли без разметки?» | Устойчивость к порогам, заложенная схема, инварианты в тестах, отметки аналитика как будущая разметка. |
| «Что при 1 млн узлов?» | Раздел «Масштабирование» в README: igraph/Leiden, BFS с битовыми масками, партиционирование, кластеры как супер-узлы. |
| «Не галлюцинирует ли ассистент?» | Отвечает только по результатам 12 функций графа, показывает цепочку вызовов, формулирует гипотезами. |
| «Без интернета работает?» | Всё, кроме LLM: пайплайн, CSV, интерфейс, PDF. cytoscape.js лежит локально. |
