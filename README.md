# Граф денег — восстановление финансовой структуры группы по транзакционной сети

Кейс HackAlem AI. Инструмент для AML-аналитика: по выгрузке исходящих переводов 81 известного клиента
(4 колена, 2 248 узлов) присваивает каждому узлу **объяснимую роль**, разбивает сеть на **кластеры**
и отвечает на вопрос **«кого смотреть первым и почему»**.

> Все выводы инструмента — **гипотезы для проверки** («признаки консолидации»), а не утверждения о виновности.

![Схема решения](docs/solution.png)

## Быстрый старт

**Вариант 1 — всё в Docker (пайплайн + PostgreSQL + интерфейс):**
```bash
cp .env.example .env          # обязательно создать; ключ OpenAI/NVIDIA внутри — по желанию
docker compose up --build     # → http://localhost:8000
```

**Вариант 2 — только выгрузки (без БД и интерфейса):**
```bash
pip install -r requirements.txt
python run.py                 # data/*.parquet → output/*.csv, ≈2 с
```

**Вариант 3 — интерфейс без Docker и без базы данных** (запасной вариант, Python 3.10+):
```bash
pip install -r requirements.txt
python run.py                             # ≈20 с: выгрузки + таблицы интерфейса в output/db/
uvicorn api.main:app --port 8000          # → http://localhost:8000 (данные читаются через DuckDB)
```
API сам выбирает хранилище: если доступен PostgreSQL (`DATABASE_URL`) — работает с ним, иначе — с локальными
файлами `output/db/*.parquet`. Принудительно: `STORAGE=postgres` или `STORAGE=local`.

**Тесты и валидация:**
```bash
pip install -r requirements-dev.txt && pytest -q     # 7 тестов, ≈10 с
python scripts/validate_planted.py --runs 10          # отчёт → docs/validation.md
```

Сценарий демо на 5 минут — [docs/DEMO.md](docs/DEMO.md).

Данные кладутся в `data/`: `edges.parquet`, `nodes.parquet`, `transactions.parquet`.

## Архитектура

```
data/*.parquet
   │
   ▼  run.py  (pipeline/)
features.py → метрики узлов (степени, суммы, коэф. пропуска, охват seed, временные признаки, центральность)
roles.py    → роль по формальным правилам с порогами из config.yaml + role_score + evidence
clusters.py → Louvain, таблица кластеров, шаблонная гипотеза
priority.py → priority_score и топ-лист с обоснованием
   │
   ├──► output/*.csv                       (обязательные выгрузки, от БД не зависят)
   └──► PostgreSQL  или  output/db/*.parquet → DuckDB (режим без базы)
            │
            ▼  api/ (FastAPI)
        REST: /api/graph, /api/node/{gid}, /api/ego/{gid}, /api/search, /api/top, /api/clusters,
              /api/path, /api/resilience, /api/assistant, /api/node/{gid}/card
            │
            ▼  frontend/ (HTML + CSS + JS, cytoscape.js)
        схема сети · поиск gid · карточка узла · топ-лист · кластеры · устойчивость · AI-ассистент
```

**LLM не участвует в расчёте ролей.** Роли, скоры и кластеры детерминированы и воспроизводимы офлайн.
LLM (OpenAI или NVIDIA API — `LLM_PROVIDER` в `.env`) используется только в интерфейсе: ассистент вызывает аналитические функции графа
(function calling) и пересказывает их результат со ссылками на gid; AI-справка по узлу собирается из его метрик.

## Метрики узла

| Метрика | Смысл |
|---|---|
| `in_deg` / `out_deg` | число уникальных плательщиков / получателей |
| `in_sum` / `out_sum` | сумма входящих / исходящих, ₸ |
| `pass_ratio` | `out_sum / in_sum` — какая доля полученного ушла дальше |
| `seed_payers` | сколько seed платят узлу напрямую |
| `seed_reach` | от скольких seed деньги доходят до узла по любой цепочке |
| `fast_share` | доля входящих денег, после которых ≥50% суммы ушло дальше за ≤2 дня (сквозной транзит) |
| `max_payers_same_day` | максимум разных плательщиков за один день (синхронные переводы) |
| `pagerank`, `betweenness` | центральность в сети (PageRank взвешен суммами) |
| `truncated` | узел на 4-м колене без исходящих — исходящие не выгружались |
| `inflow_incomplete` | входящие видны не полностью (seed или отдаёт >1.2× видимого входа) |
| `hub_payers` | сколько узлов-хабов (coordinator / consolidator / distributor) платят узлу |
| `split_out` / `split_in` / `split_tx` | эпизоды дробления как отправитель / получатель, число переводов в них |
| `near_threshold_share` | доля переводов 5–10 тыс ₸ (у нижнего порога выгрузки) |
| `role_stability` / `alt_role` | доля из 60 вариантов порогов (±20%), где роль сохраняется / самая частая альтернатива |
| `anomaly_score` / `anomaly_text` | насколько суммы узла выбиваются из активных узлов его колена (robust z по log-шкале) |
| `routes_mid` | в скольких повторяющихся маршрутах A→B→C узел — посредник B |
| `cycles` / `reciprocal` | число возвратных цепочек длиной ≤4 через узел / встречных пар A⇄B |

## Правила ролей

Роли проверяются по порядку, узел получает **первую** подходящую. Пороги — в `pipeline/config.yaml`.

| # | Роль | Правило | role_score |
|---|---|---|---|
| 1 | **coordinator** | (а) `in_deg ≥ 5` **и** `out_deg ≥ 10` — одновременно собирает и раздаёт; (б) *второй проход*: консолидатор, которому платят `≥ 6` узлов-хабов и до которого доходят деньги `≥ 5` seed — **сборщик второго уровня** | (а) среднее насыщение по in/out; (б) 0.6·насыщение по hub_payers + 0.4·по seed_reach |
| 2 | **distributor** | `out_deg ≥ 10` — веерная рассылка | насыщение по out_deg |
| 3 | **consolidator** | `in_deg ≥ 5` — сбор с нескольких плательщиков | насыщение по in_deg + бонус за seed-плательщиков |
| 4 | **transit** | не seed, `in_sum ≥ 50 тыс`, есть исходящие, `0.8 ≤ pass_ratio ≤ 1.2` | близость pass_ratio к 1 + доля быстрого пропуска |
| 5 | **terminal** | не на границе выгрузки, (`out_deg = 0` или `pass_ratio ≤ 0.2`), (`in_sum ≥ 200 тыс` или `in_deg ≥ 2`) | перцентиль in_sum |
| 6 | **boundary** *(расширение)* | 4-е колено, исходящих нет → судьба денег неизвестна | 0.9 |
| 7 | **peripheral** | ничего из перечисленного | 1 − близость к порогам ролей |

«Насыщение» = 0.5 ровно на пороге и 1.0 на максимуме по сети (логарифмическая шкала).

**Почему добавлена роль `boundary`.** 444 узла 4-го колена имеют нулевые исходящие только потому, что обход на
них остановлен. Наивное правило «нет исходящих ⇒ конечный получатель» дало бы 444 ложных стока. Мы
отделяем их в явную роль; если строго нужен базовый словарь — `use_boundary_role: false` в конфиге.

**Почему у крупных распределителей out ≫ in.** Выгрузка содержит только переводы, исходящие из seed-цепочек;
входящие из-за пределов выборки не видны. Такие узлы помечаются в evidence: «отдаёт в N× больше видимого входа —
есть внешние источники». Это сигнал для следующего запроса данных.

## Приоритет

```
priority = 0.35 · (вес роли × role_score) + 0.25 · перцентиль оборота
         + 0.20 · перцентиль охвата seed + 0.20 · перцентиль центральности
priority ×= 0.75 для seed (уже известны — фокус на тех, кто выше по цепочке)
нормировка в 0–1
```
Веса ролей: coordinator 1.0 · consolidator 0.85 · distributor 0.8 · transit 0.6 · terminal 0.45 · boundary 0.3 · peripheral 0.1.

## Кластеры

Louvain на неориентированном графе, вес ребра = `log(1 + сумма)`, `seed=42` для воспроизводимости.
Узлы без рёбер (seed без переводов ≥5 000 ₸) — кластер 0. Гипотеза кластера формируется по составу ролей:
число seed, главный узел-сборщик, наличие распределителей, транзитов, конечных получателей, внутренний оборот.

## Как мы проверяем, что роли обоснованы

Эталонной разметки нет, поэтому обоснованность проверяется тремя независимыми способами:

1. **Устойчивость к порогам** (`role_stability`). Роли пересчитываются 60 раз, каждый порог сдвигается случайно
   в пределах ±20%. Средняя устойчивость — **97%**; coordinator и distributor сохраняются в ~90% вариантов,
   consolidator — в ~71% (самая чувствительная роль). 94 узла с устойчивостью < 70% помечены в карточке как
   «пограничные» с указанием альтернативной роли — аналитик видит, где вывод держится на одном пороге.
2. **Заложенная схема** (`scripts/validate_planted.py`, [отчёт](docs/validation.md)). В реальный граф встраивается группа
   с известными ролями и контрольная группа случайных переводов. За 10 прогонов: все роли распознаны в 100% случаев,
   узлы 4-го колена не принимаются за конечных получателей, ложных хабов на шуме — 0.
3. **Инварианты в тестах** (`tests/`). Каждая роль удовлетворяет своему правилу из конфига, seed никогда не transit,
   обрезанные узлы никогда не terminal, результат детерминирован.

Плюс обратная связь: аналитик отмечает гипотезы «подтверждено / на проверке / отклонено» — это накопит разметку
для будущей калибровки порогов.

## Учёт ограничений данных

| Ограничение | Как учтено |
|---|---|
| Обрыв на 4-м колене | роль `boundary`, не путаем с terminal |
| Только исходящие переводы | флаг `inflow_incomplete`, оговорка в evidence и карточке |
| У seed занижены входящие | seed не могут быть transit; коэффициент пропуска для seed не используется |
| Порог 5 000 ₸ | дробление ниже порога невидимо — указано как ограничение |
| 19 seed без рёбер | все в `nodes_roles.csv`, кластер 0 с гипотезой |
| 16 компонент | Louvain работает на всех компонентах; устойчивость считает компоненты |
| Нет ground truth | оценка — по обоснованности правил; все пороги в одном конфиге |

## Дополнительно реализовано

- **Временные паттерны:** сквозной транзит за ≤2 дня, синхронные переводы от нескольких плательщиков в один день, дневная активность в карточке.
- **Сборщики второго уровня:** узлы, куда стекаются деньги от других сборщиков и распределителей (второй проход правил).
- **Детекция дробления:** ≥3 перевода одной паре клиентов в один день (93 эпизода, 91 узел; самая выраженная пара — 58 переводов за 9 дней). Это признак-аномалия поверх роли, отражается в evidence, why, карточке и `splitting.csv`.
- **Устойчивость ролей и разложение приоритета:** в карточке узла — в скольких вариантах порогов роль сохраняется и
  из каких вкладов (роль, деньги, охват seed, центральность) сложился priority_score.
- **Аномалии относительно колена:** узлы, чьи суммы или средний перевод в десятки раз выше медианы активных узлов того же
  колена (20 узлов). Находит то, что правила ролей пропускают: например, «периферийный» узел с входом 3,1 млн ₸ (в 58× выше медианы).
- **Повторяющиеся маршруты A→B→C:** A платит B, B в течение 3 дней платит C, повторилось ≥3 раз (174 маршрута).
- **Проигрыватель июля:** кнопка «▶ Июль» — переводы по дням на схеме сети, по дню или накопительно.
- **Потоки денег (санкей):** куда уходят средства seed по коленам и ролям; толщина ленты — сумма.
- **Отметки аналитика:** «подтверждено / на проверке / отклонено» + комментарий; хранятся в PostgreSQL
  (таблица `analyst_marks`, не стирается при пересчёте) или в `output/analyst_marks.json`; попадают в PDF-справку.
- **PDF-справка по узлу:** кнопка «PDF» в карточке открывает печатную справку (роль и обоснование, показатели, признаки, контрагенты, эпизоды дробления, возвратные потоки, хронология, ограничения данных, рекомендуемые действия и запросы). Сохраняется через «Печать → Сохранить как PDF»; по кнопке добавляется AI-резюме.
- **Возвратные потоки:** циклы A→B→…→A длиной до 4 (387 циклов, 298 узлов), цепочки с суммами — в карточке узла.
- **Оценка полноты:** вкладка «Пробелы» и `next_requests.csv` — чьи исходящие дозапросить (узлы за границей выгрузки) и чьи входящие (узлы, отдающие больше видимого входа).
- **Устойчивость сети:** что будет при блокировке топ-N — число компонент, размер крупнейшей, охват от seed, доля отрезанного оборота.
- **AI-ассистент** (OpenAI / NVIDIA, function calling): `get_node`, `get_neighbors`, `common_receivers`, `trace_path`, `top_nodes`, `cluster_summary`, `simulate_removal`, `find_cycles`, `find_splitting`, `find_routes`, `anomalies`, `next_requests`.
- **AI-справка по узлу:** роль, потоки, на что обратить внимание, какой запрос сделать следующим.

## Масштабирование до ~1 млн узлов

- **Вычисления:** networkx → igraph / graph-tool / cuGraph (C/C++, в 10–100 раз быстрее); betweenness — только аппроксимация по выборке источников; Louvain → Leiden (igraph / leidenalg).
- **Охват seed:** вместо `ancestors` для каждого узла — один проход BFS от каждого seed с битовыми масками.
- **Хранение:** рёбра в PostgreSQL с партиционированием по периоду, либо графовая БД (Neo4j / Memgraph) для обходов; агрегаты по узлам — материализованные представления.
- **Инкрементальность:** пересчёт метрик только для узлов, затронутых новыми транзакциями; роли — правилами поверх обновлённых метрик.
- **Интерфейс:** не отдаём весь граф — сначала кластеры как супер-узлы, раскрытие кластера и окрестности по запросу; укладка считается на сервере заранее.

## Ограничения подхода

- Пороги подобраны по распределениям этой выгрузки; для другого периода или банка их нужно перекалибровать.
- Роли определяются по структуре и суммам — без атрибутов клиента и типа операции возможны ложные срабатывания (например, легальные бизнес-счета с большим числом плательщиков).
- Внутрибанковские переводы only: цепочки через другие банки и наличные не видны.
